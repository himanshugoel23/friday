# Agent team: Query Understanding, PM, site agents, all over A2A (BUILT 2026-10-28, all switches OFF)

Status: built and tested with fakes only. Nothing here has run against the real OpenAI API, the real Zomato/Swiggy sites, or a real phone. All new chat lines are PENDING founder approval (list at the end). No spoken (voice) line was touched.

## 1. What was asked, in one picture

```
 user text (web chat / WhatsApp text)
   |
   v   [1] QUERY UNDERSTANDING AGENT   friday/speech/query_agent.py   (shared with the voice-note understander)
   |       lingo -> user dictionary + fuzzy match -> shared SpeechUnderstander (model, grounding, floor) -> ONE instruction
   |       unsure about a name? -> ONE question, nothing changed silently
   v   [2] PROJECT MANAGER             friday/team/pm.py     (only manages: split, delegate, check, merge, reply)
   |
   |   small task (< 3 goals)          PM  --A2A-->  specialists (zomato | swiggy | web_lookup)
   |
   |   big task (>= 3 goals)           lead PM --A2A--> sub-PM 1..n --A2A--> specialists
   |                                   depth max 2; a sub-PM reaches ONLY specialists and reports ONLY to the lead;
   |                                   ONE budget (steps, seconds, cost) shared down the tree; one root task id, child task ids
   v   [3] lead PM alone talks to the user: ONE merged reply (failed parts named, never hidden)
   |
   v   anything the team does not do (calls, bookings...) continues unchanged: planner -> browser -> quotes -> PM -> brain
```
Code: `friday/a2a` (protocol), `friday/speech` (query agent, fuzzy, user dictionary), `friday/team` (PM, site agents, knowledge, drift, gateway). Hook: `InboundPipeline._active` after chatbot/features, before the planner. Switches: `FRIDAY_QUERY_UNDERSTANDING_ENABLED`, `FRIDAY_AGENT_TEAM_ENABLED` (independent), `FRIDAY_A2A_HTTP_ENABLED`, `FRIDAY_TEAM_DRIFT_ENABLED`; all default OFF; the first two are switched on by `deploy/enable-web-test.sh`, the last two only by hand. `FRIDAY_A2A_HTTP_TOKEN` (name only) is required for HTTP; no token = every HTTP call gets 403.

## 2. Query Understanding Agent (Wispr-style, for TEXT)
Reuses, does not copy, `friday/speech`: the same `SpeechUnderstander.understand(..., force=True)` does fillers, self-corrections ("kal nahi, parso"), grounding (no invented number, day or name), the model deadline (`FRIDAY_QUERY_UNDERSTANDING_TIMEOUT_S`, default 2.5 s), the rules floor, and the raw-words fallback. Rules kept: original text always kept (`raw['original_text']`); never applied to a vendor's speech; OTP/PIN talk is passed through untouched; never raises.
Added for text: (a) shared lingo (`pls, tmrw, rn, resto ...`, `speech/data/lingo.json`, no numbers, no names); (b) the USER-SPECIFIC layer below.

**User dictionary (per user, DPDP-erasable).** Entities come from what Friday already knows: profile city, saved Places (label, aliases, city, address pieces), People (+ first names), known shops, plus dictionary entries stored as `Fact` rows (`dict:<kind>:<word>`; no migration, shows in "what do you remember about me", removed by "forget ..." and by the delete-everything flow). Chat commands: `my words`, `add place|shop|name|word <X>`, `forget word <X>`, `forget all my words`. Secrets, phone numbers, e-mails and long digit runs are refused.
**Fuzzy match** (`speech/fuzzy.py`): Damerau-Levenshtein plus a phonetic consonant skeleton tuned for Indian transliteration (th/t, ph/f, w/v, ee/i/e merge). Windows of 1-3 words ("sone pat"). Outcomes: saved alias -> fix; score >= 0.84 with an identical skeleton, a place/shop/word, and a clear margin over the next entity -> silent fix; 0.70-0.84, or ANY person's name, or two close entities -> ASK ("Did you mean Priya Sharma?"); ordinary words (stop list), words under 4 letters and already-correct words are never touched. "Soneepat / sonipath / Sonepat / sone pat / soni pat" -> "Sonipat" for a user who lives there; "Rohtak" is left alone.
**Learning** reuses the memory rule: a fixed spelling is a sighting; after 2 sightings or 1 tap ("yes") it becomes a saved heard form (Person/Place rows through `MemoryService.note_misheard`, everything else in the dictionary). "No" keeps the user's own spelling and is not asked again.

## 3. A2A (friday/a2a)
Wire types follow Google Agent2Agent as the builder remembers it: Agent Card (name, description, url, version, protocolVersion, capabilities, skills, input/output modes) at `/.well-known/agent.json`; `message/send`, `tasks/get`, `tasks/cancel`; Message/Part (text, data), Task, Artifact; states submitted, working, input-required, completed, canceled, failed (+ rejected, auth-required, unknown); JSON-RPC 2.0 with the standard error codes. **Honest limits: the spec text was NOT re-fetched while building (verify the field names and version before talking to any third-party A2A agent); streaming (`message/stream`) and push notifications are NOT implemented (the card says so); `capabilities`/auth schemes are minimal.**
`A2AServer` wraps any handler (card + `handle(call) -> reply`); `A2AClient` adds discovery by skill, budget check BEFORE sending, time-box, audit of request and response, and `delegate()` (agent trouble becomes a failed task, never a crash). Transports: `InProcessTransport` (default; still serialises to full JSON-RPC dicts, so the in-process path is real A2A) and `HttpTransport` (+ `friday/a2a/http.py` router, bearer token, behind a switch). **Agents never call each other's Python**: the PM module imports no specialist (a test asserts it); a sub-PM's transport contains specialists only, and the server refuses depth > 2.
**Audit** (`A2AAudit`): every message is logged with sender, receiver, method, task / root / parent ids, depth, state and a MASKED, clipped text (`redact_secrets`, e-mails, phones masked to the last 2 digits); ring buffer + optional JSONL under `var/team_knowledge/a2a_audit.jsonl`.
**Budget** (`TaskBudget`): per user task, shared by reference down the tree: max steps (A2A requests, default 30), max seconds (40), max cost (INR 8). When one is hit the PM stops dispatching, keeps what it has and replies with it plus a "stopped early" line. Cost per web search is a GUESS (INR 1.0), reported by specialists in task metadata; not measured.

## 4. Small vs big task (deterministic, no model)
Clauses are split on `; , and also, then, aur, plus` (a clause with no domain of its own, e.g. "with extra raita", joins the goal before it) and classified: food (dish or food app + food context), web (planner heuristic says WEB_LOOKUP with confidence >= 0.8), other (call/booking/local service/app order: left to the old chain). **Size rule: team-handled goals >= 3 (`FRIDAY_TEAM_BIG_GOAL_THRESHOLD`) = big.** Big: one sub-PM per goal, capped at 4 (`FRIDAY_TEAM_MAX_SUB_PMS`); extra goals join the last sub-PM. A failed sub-PM is reported up as "failed" and the lead carries on; the user sees "I could not finish this part: ..." for it and the real results for the rest. A single web-price goal still goes to the approach planner (pincode follow-ups and cache live there); the team takes food goals and multi-goal requests. Pending state (a yes/no, an area) is in memory: lost on restart, expires in 10 minutes.

## 5. Site agents (Zomato, Swiggy)
Each is an A2A agent (skill `food.search`) with ONE versioned knowledge file (`friday/team/knowledge/<site>.v1.json`, data not code): search flow, URL patterns with confidence, where name/rating/price/delivery time/offers live, login and checkout steps, quirks, anti-bot behaviour, safety rules, probes. Search = OpenAI Responses `web_search` through the existing WEB_LOOKUP port (`hint` argument gives the food instructions). Grounding in code: an option needs a URL the provider cited AND that is on the site's own domain; a price number is dropped if it disagrees with its printed text; the price cap filters only options whose price is known (unknown prices are shown as "price not shown"); nothing invented. Output: options (name, price, rating, delivery time, offer, deep link), sources, as-of (IST), search link, knowledge version and status. **Friday never orders and never pays**: the reply ends with "open a link and order in your own app"; real order flows stay behind the browser connector and its stop-at-payment rule, and `safety` in the knowledge file cannot be changed by any proposal. Needs the area: a missing area makes the agent answer `input-required`, the PM asks one question, and the user's reply CONTINUES the same A2A task id.
**Honest limits.** The v1 knowledge was written from general knowledge of the sites and is marked `unverified`; selectors are not used at all (search, not scraping). Menu prices are script-loaded, so web search often shows "cost for two" instead of a dish price; many results will say "price not shown". Public page fetch for enrichment is NOT built into the agent (only the drift probes fetch pages). The Zomato/Swiggy official MCP route stays a later option.

## 6. Self-checking and learning (friday/team/drift.py, knowledge.py)
A job in the existing runtime (`team_drift_loop`, role task, polls every 30 min, does real work at most once per `FRIDAY_TEAM_DRIFT_INTERVAL_H` = 24 h): for each site, at most 4 probe pages; robots.txt is read first (unreadable = do not fetch); per-host rate limit (6 s); no login, no cookies, identifying User-Agent. Outcomes per probe: ok, moved (redirect), marker_missing, gone, blocked, skipped_robots, error. **A bot challenge / 403 / 429 / timeout = `unverified`: the agent keeps the last good version, we never try to get around it.** Honest note: from a cloud droplet Zomato and Swiggy will often show challenges or refuse, so expect `unverified` much of the time; the agent then says its notes are unverified.
Drift becomes a PROPOSAL = a new version with a diff. `validate` (schema, https + known domains for every URL, version = previous + 1, size) refuses any change to `safety`, `domains`, `schema`, `anti_bot.our_response` or `login_checkout.stop_rule`. **Auto-apply only if** it validates, every changed path is a URL/observed path (`url_patterns.*`, `probes.N.url`, `observed.*`), and every new URL was fetched successfully by the job in that same run. Anything else (marker missing, page gone, notes) goes to the review queue (`<dir>/review/*.json`), decided with `friday team review|approve|reject`. Versions are never deleted; `friday team rollback <site> <n>` moves the CURRENT pointer; every event is in `changelog.jsonl`. The agent never rewrites code, prompts or safety rules.

## 7. Trade-offs, latency and RAM (1 GB droplet; ALL figures are estimates, not measurements)
* In-process A2A: zero extra processes; JSON (de)serialisation per hop is microseconds against 2-20 s web searches. Extra RAM is a few MB of Python objects (a few small pydantic models and a ring buffer of 500 audit rows). This is why it is the default.
* HTTP transport: each agent in its own process would cost roughly 60-120 MB each (Python + pydantic + httpx), i.e. a 1 GB box cannot host the team that way next to the web app and swap; use HTTP only to reach an agent on ANOTHER host. Added latency per hop is a few ms locally, more across hosts.
* Latency of the user-visible path: query understanding adds <5 ms for rules + fuzzy and up to the model deadline (2.5 s, off the hot path of nothing else); a food request is dominated by one OpenAI web_search call per site (several seconds, UNMEASURED); two sites run in parallel; a big request runs its sub-PMs in parallel, bounded by the 40 s budget. One "on it" line goes out after 8 s (existing slow-response helper).
* Cost: one web search per site per food goal (budget guess INR 1 each, cap INR 8 per request); the query-understanding model call is the existing small model.
* Hierarchy depth 2 is a hard cap; more levels would add latency and budget leakage for no gain at this size.
* Known weak spots: pending yes/no and area answers are in memory (restart loses them); a big request holds all replies until the slowest sub-PM finishes (or the budget time ends); the heuristic clause splitter will misjudge unusual phrasing (then the old chain runs, never a wrong order: the team only searches).
